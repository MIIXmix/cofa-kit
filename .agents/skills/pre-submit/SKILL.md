# 제출 전 점검 + 서술형 리허설

## A0. 기계 점검 먼저 (작업 폴더 루트에서)
```
python3 .agents/skills/pre-submit/scripts/cofa_check.py --raw <원본 폴더나 파일> --pii-source <식별 열이 있는 원본 CSV> --pii-cols <열1,열2>
```
- `python3`가 없으면 `python`으로 실행한다.
- 과제가 정한 필수 파일명이 다르면 `--require 파일1,파일2`로 바꾼다. 개인정보가 없을 때만 `--pii-*`를 뺀다. 개인정보나 원본이 있는데 해당 검사가 SKIP이면 통과가 아니다.
- FAIL이 0이 될 때까지 출력의 "고치는 법"대로 고치고 다시 돌린다. WARN은 이유를 NOTES.md 남은 한계에 1줄 적거나 고친다. 가명 ID 키가 든 `.env`는 재발급하지 말고 보고한다.
- 마지막 실행의 출력 전체를 `evidence/5_done.md`에 붙이고 커밋한다(막혔으면 커밋 명령을 사람에게 준다).
- 스크립트가 보는 항목: 아래 1(필수 파일), 3(NOTES 절), 5(원본 변경), 8(미커밋), 디버그 모드와 innerHTML, `.env` 추적. 부분만 보는 항목: 2(원본 값 문자열 일치만, 가명 ID 사용 여부와 `--pii-min-len`보다 짧은 값은 못 봄), 10(requirements.txt만, package.json은 못 봄). 나머지(2와 10의 남는 부분, 4, 6, 7, 9, 11, 12)는 아래 표로 손 점검한다.

## A. 점검표 (명령으로 확인하고 결과를 표로)
1. README·담당자가 요구한 필수 파일이 정해진 이름·경로에 모두 있는가
2. 식별정보 0건: 원본의 이름·사번·전화·이메일 값 일부를 결과물 폴더에서 grep → 0건이어야 함. 앱이 로그인 ID나 키로 쓰는 값은 가명 ID인지 확인
3. NOTES.md에 5개 절이 있는가: 판단과 근거 / 결정 카드 / 검증 결과 / 남은 한계 / 데이터 처리(제외·환산·중복·인젝션 기록)
4. REQUIREMENTS.md 각 항목이 결과물 어디에 반영됐는가 (항목 → 파일·위치 대조표)
5. 원본 파일이 바뀌지 않았는가 (`git diff --stat`으로 원본 경로 변경 0건, 내용 diff는 출력하지 않음)
6. "조용한 실패" 확인: 판정 제외·데이터 없음·기간 밀림이 결과물 첫 화면이나 맨 앞에 경고로 드러나는가
7. 웹 서비스면 Browser 미리보기로 핵심 기능 1회 실행 확인
8. 미커밋 변경 없음 (git status, 설치 전부터 있던 최상위 숨김 미추적 경로는 `.cofa_baseline` 기준으로 뺀다. 그런 폴더(예: 미리 있던 `.vscode/`) 안에 만든 작업물은 스크립트가 못 보니 직접 확인한다). 커밋이 막힌 환경이면 남은 커밋 명령을 사람에게 준다
9. 웹 서비스면: 서버를 끄고 README 4줄만으로 새 터미널에서 다시 띄워지는가, 자동 테스트 전체 통과 수, Browser 점검표 X 0건
10. 의존성 파일에 실제 import한 패키지가 모두 있는가, 코드·설정에 키·비밀번호 하드코딩 0건(grep)
11. PLAN.md의 "하지 않음"·미완성 항목이 NOTES.md 남은 한계에 적혀 있는가
12. NOTES.md 결정 카드가 핵심 방법·보안·저장 구조마다 있고, 카드의 파라미터 값이 설정 파일의 실제 값과 같은가

## B. 서술형 예상 질문 6개 (답은 쓰지 않는다 — 내가 AI 없이 답한다)
산출물과 git log·NOTES.md·결정 카드를 근거로 만든다. 결과물 형태에 맞는 갈래를 쓴다.

웹 서비스형:
1. 핵심 방법(알고리즘, 데이터 결합, 군집 등)을 왜 그렇게 골랐나, 대안은 무엇이었나
2. 계획이나 설명 문서(과제가 정한 이름의 문서) 안 특정 결정의 이유
3. 로그인, 권한, 개인정보, 보안을 왜 그렇게 설계했나
4. 엣지 시나리오 동작: 새 데이터 업로드, 직후 옛 데이터 재업로드, 빈 입력, 동시 요청에서 무슨 일이 생기고 어떻게 막나
5. 배포에서 생긴(생길) 문제: 시크릿 키, 환경 차이, 재시작
6. AI 협업: 무엇을 맡기고 왜 그렇게 나눴나, 어떻게 검증했나, 어떤 제안을 거절했나

분석 보고서형:
1. 결론의 약점·장애 상황 (경계값 사례, 결론이 뒤집히는 조건)
2. 숫자 출처 (어느 파일 몇 행·어느 조항)
3. 판단 위임 항목의 기준과 이유
4. 핵심 방법을 왜 골랐나, 대안은
5. 개인정보·인젝션 처리
6. AI 결과를 어떻게 검증했나, 어떤 제안을 거절했나

두 갈래 공통으로 아래 각도 중 결과물에 해당하는 것을 위 6개 중 약한 것과 바꿔 넣는다(서술형 문항은 사람마다 다르게 나온다):
- 모듈 간 데이터 흐름: 어느 파일이 무엇을 만들고 누가 읽나, 상태(현재 버전, 결과)는 누가 소유하나
- 구현한 것과 가정한 것의 구분: 무엇이 실제로 동작하고 무엇이 가정인가, 채점자가 어디서 확인하나
- COLLAB_LOG.md에 적은 오류 하나를 어떻게 진단하고 확인했나(발견, AI 진단, 내 판단, 확인)
- 조건이 바뀌면(정원, 시간 상한, 데이터 갱신) 어떤 검사를 다시 돌리나

각 질문 아래에 "답에 반드시 들어가야 할 숫자·파일명"만 괄호로 적는다.
답 형식 안내: 설계형(이유, 방법, 협업)은 결정 → 대안과 버린 이유 → 위험과 대응. 장애형(엣지, 배포, 약점)은 약점(숫자) → 파급(무엇이 몇으로 바뀌나) → 조치(실행 단계 3개).

## C. 내가 직접 읽기 (5분, AI 없이)
서술형은 붙여넣기가 막혀 기억한 것만 쓸 수 있다. 제출 직전 내가 직접 읽는다:
NOTES.md 결정 카드 전부(동작 설명 5줄을 소리 내어 말해 본다) → `git log --oneline` 전체 → COLLAB_LOG.md 거절·수정 항목과 오류 진단 기록 → NOTES.md 남은 한계 → B의 괄호 속 숫자·파일명.
