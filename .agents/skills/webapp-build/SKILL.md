# 웹 서비스 구현

## 1. 스택 결정 (첫 단위 전에 1회, 근거와 함께 보고)
1. 과제가 제공한 시작 코드·package.json·requirements.txt가 있으면 그 스택을 그대로 쓴다.
2. 없으면 설치 확인(`node --version`, `python3 --version`, `pip --version`) 후 의존성이 가장 적은 조합을 고른다.
   기본값: Python FastAPI(또는 Flask) + 정적 HTML/JS 1페이지 + 저장은 JSON 또는 SQLite 파일.
   프런트 빌드 도구(React·Vite 등)는 과제가 요구할 때만 쓴다.
3. 의존성은 requirements.txt 또는 package.json에 버전과 함께 적는다.
4. 패키지 설치가 실패하면(네트워크 차단 등) 재시도는 1회만. 이후 설치 없이 되는 것으로 전환한다: Node 내장 `http` 모듈 또는 Python 표준 라이브러리 `http.server` + `json`/`sqlite3`. 전환 사실을 COLLAB_LOG.md에 기록한다.

## 2. 서버 규칙
- 호스트 0.0.0.0, 포트는 환경변수 PORT(기본 8000 등)로 받고 시작 시 "listening on 0.0.0.0:<포트>"를 출력한다.
- 서버처럼 계속 실행되는 명령은 Codex가 직접 붙잡고 있지 않는다. 실행 명령 한 줄을 나에게 주고, 내가 별도 터미널 탭에서 실행한다.
- 코드 변경 후 재시작이 필요하면 그렇다고 말한다(자동 리로드 옵션이 있으면 사용).

## 3. 구현 순서 (PLAN.md의 세로 단위마다 반복)
1. 로직 함수 → API → 화면 순으로 한 기능을 끝까지 만든다.
2. 해당 기능의 자동 테스트를 같이 만든다(webapp-test 스킬 기준) 후 실행해 결과 숫자를 보고한다.
3. Browser 미리보기에서 내가 확인할 것 3줄 이내: 포트, 경로, 누를 것과 기대 화면.
4. 커밋(메인만, 그 단위 파일 경로만 add): "[단위N] 기능명 — 수용 기준 #번호 충족". 서로 다른 기능의 로직 함수와 그 테스트처럼 파일이 겹치지 않는 단위는 AGENTS.md 8-7에 따라 병렬로 맡긴다. 진입 파일(라우트 등록, index.html)을 고치는 단위는 공용 파일 단위라 혼자 둔다.

## 4. 화면이 반드시 처리할 상태
- 빈 데이터, 잘못된 입력(오류 문구), 처리 중, 실패(서버 오류) 상태를 화면에 표시한다. 조용히 아무 일도 안 일어나는 버튼은 없게 한다.
- 판정·경고·제외 같은 중요한 결과는 첫 화면 위쪽에 보이게 한다.
- 다른 사람의 개인정보는 화면·로그·응답에 출력하지 않는다(AGENTS.md 2번). 로그인한 본인 데이터 표시는 6장 기준을 따른다.

## 5. 마무리
README.md에 "설치 → 실행 → 접속 경로 → 테스트 실행" 4줄을 쓴다. 새 터미널에서 이 4줄만으로 다시 띄워지는지 확인한다.

## 6. 보안·배포 기본값 (계획 단계에서 채택, 지시가 없어도 기본으로 제안)
과제 안내나 담당자 답이 다르게 정하면 그것을 따른다. 채택한 항목은 PLAN.md 수용 기준 표에 MVP 행으로 넣고 테스트를 붙인다(plan-and-scope 5번). NOTES.md에는 "보안" 결정 카드 1장을 두고 항목별로 한 줄씩 쓴다. 괄호 안 문장은 서술형에서 내가 쓸 설명이다.
필수(시간이 없어도): 1, 3, 4, 6, 9. 나머지는 담당자가 요구했거나 여유가 있을 때.
1. 권한: 이용자와 운영자 역할을 서버 API에서 검사한다. 화면 버튼 숨기기만으로 막지 않는다. (API를 직접 불러도 막혀야 보안이다.)
2. 로그인: 사내 SSO가 있다고 하면 연동 지점만 두고 가정을 기록한다. 자체 계정이면 비밀번호는 사용자별 랜덤 salt와 함께 해시로만 저장(bcrypt, 설치가 막히면 표준 `hashlib.scrypt` + `os.urandom(16)` salt), 비교는 `hmac.compare_digest`. 세션 쿠키는 HttpOnly, SameSite=Lax, 상태를 바꾸는 요청은 POST 이상만. 로그인 실패 메시지는 "아이디 또는 비밀번호가 틀림" 하나로 통일. (원문 비밀번호가 없으니 DB가 새도 비밀번호는 안 샌다. 스크립트가 쿠키를 읽지 못하고, 다른 사이트에서 보낸 요청에는 쿠키가 붙지 않는다.)
3. 시크릿: SECRET_KEY, DB 비밀번호, 가명 ID 키는 `.env` 파일(또는 환경변수)로만 받고 코드에 기본값을 두지 않는다. 시작할 때마다 랜덤 생성하지 않는다. `.env`는 `.gitignore`와 `.dockerignore`에 넣고 `.env.example`(가짜 값)만 커밋한다. README 설치 줄에 `cp .env.example .env`를 넣고, compose는 `env_file: .env`를 쓴다. 운영 모드에서 값이 없거나 `.env.example`의 가짜 값 그대로면 기동을 거부한다. (코드에 키가 있으면 저장소를 본 누구나 로그인 토큰을 위조한다. 재시작마다 키가 바뀌면 전원 로그아웃되고, 서버가 여러 대면 서로 토큰을 못 읽는다.)
4. 개인정보 화면: 이용자는 자기 정보만 본다. 운영자 화면의 주소와 좌표는 마스킹(시군구, 소수 2자리)이 기본이고, 원문이 꼭 필요하면 권한을 나눈다. 로그에는 주소, 좌표, 사번 원문을 남기지 않는다.
5. 사내망: 외부 CDN, 웹폰트, 지도 타일, 외부 API를 쓰지 않는다. 필요한 JS와 CSS는 저장소에 같이 넣는다. 지도가 필요하면 좌표를 SVG나 canvas로 직접 그린다. (사내망은 외부가 막혀 있고, 외부 호출은 데이터 유출 경로가 된다.)
6. CSV 업로드와 내려받기: 파일 크기 상한, 필수 열과 형식 검사. 인코딩은 `utf-8-sig`(엑셀 UTF-8의 BOM 제거)로 먼저 읽고 실패하면 `cp949`로 읽는다. 열 이름은 앞뒤 공백을 지운 뒤 검사한다. 내려받는 CSV는 BOM을 붙여 쓰고(`utf-8-sig`, 엑셀 한글 깨짐 방지), 숫자가 아닌 문자열 셀이 `=`, `+`, `-`, `@`, 탭, CR로 시작하면 앞에 `'`를 붙인다. 업로드 정규화에서는 이렇게 붙은 앞 `'`를 다시 지운다. (엑셀이 그 셀을 수식으로 실행하는 CSV 인젝션을 막고, 내려받은 파일을 그대로 다시 올려도 같은 데이터로 인식한다.)
7. 배포: 과제가 도커나 서버를 주면 Dockerfile과 docker-compose.yml을 만들고, 설정은 전부 환경변수로, 상태 확인 경로 `/health`를 둔다. 데이터 파일은 볼륨에 둔다. README에 도커 실행 1줄을 더한다.
8. 데이터 갱신형 앱(운영자가 새 파일을 올리는 경우):
   - 필수: 업로드마다 정규화(공백 정리, 키 기준 정렬) 후 내용 해시를 계산하고 버전을 덮어쓰지 않고 새로 저장한다. "현재 버전" 표시만 옮긴다.
   - 필수: 계산 결과는 (데이터 해시, 설정 파일 해시, 코드 버전 = git 커밋) 세 값이 모두 같을 때만 재사용한다. 데이터만 같고 가중치나 코드가 바뀌었으면 다시 계산한다. (새 데이터를 넣었다가 바로 옛 데이터를 다시 넣으면 옛 결과가 그대로 돌아오고, 그사이 설정을 바꿨다면 새 설정으로 다시 계산된다.)
   - 필수: 결과는 다 만든 뒤 한 번에 현재 버전으로 바꾼다. (반쯤 바뀐 결과가 보이지 않는다.)
   - 여유: 이전 현재 버전과 키 기준 diff(추가, 삭제, 필드 변경)를 화면에 보여 준다. 담당자가 변경 내역 화면을 요구했으면 필수로 올린다.
   - 여유: 재계산은 백그라운드 작업 1개씩, 계산 중 업로드는 대기열.
   - 여유: 결과 ID(묶음 번호 등)를 이전 버전과 최대한 같게 유지한다. (이용자가 보던 화면이 깨지지 않는다.)
   - 여유: 업로드 이력(시각, 올린 사람, 해시, 추가/삭제/변경 수).
9. 웹 기본 방어: 업로드 값과 사용자 입력은 화면에 `textContent`로만 넣고 `innerHTML`에 넣지 않는다(XSS 방지). SQL은 매개변수 쿼리만 쓴다(문자열 이어 붙이기 금지). 디버그 모드는 끈다(Flask `debug=False`, FastAPI `reload`는 개발 때만). (0.0.0.0으로 열린 서버에서 디버그 모드가 켜져 있으면 원격으로 코드를 실행당할 수 있다.)
