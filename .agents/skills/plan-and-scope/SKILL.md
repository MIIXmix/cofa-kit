# 계획·범위 + 협업 기록

과제 안내에 계획 문서·협업 기록의 파일명이나 양식이 있으면 그것을 따른다. 없을 때만 아래 PLAN.md / COLLAB_LOG.md를 쓴다.

## 1. PLAN.md (구현 전에 작성, 내 승인 후 진행)
0-0. 최적화 생략 관문: 데이터에 이미 결과물(경로, 거점, 배정, 일정 등 현행안)이 있으면 새로 최적화하기 전에 과제가 "현행안 평가와 개선"인지 "새로 설계"인지 README와 담당자 답으로 확인한다. 확인 전에는 현행안을 그대로 읽어 지표만 계산한다. 새로 설계하더라도 현행안을 기준선(modeling-options 3장 3번)으로 쓴다.
0. 방법 선택: 데이터를 조합하고 묶고 나누고 배정하는 문제면 modeling-options 스킬로 유형을 판정하고, 결과가 갈리는 유형만 후보 2~3개와 추천 1개를 나에게 보여 주고, 최적화면 방법 수준(modeling-options 4장)도 고르게 한다. 5분 안에 내 답이 없으면 추천안으로 진행하되 방법 수준은 1단계로 둔다. 고른 안을 NOTES.md 결정 카드(AGENTS.md 7-1)에 적은 뒤 아래로 넘어간다.
1. 목표 1문장: 누가, 어떤 상황에서, 무엇을 할 수 있게 되는가
2. 사용 시나리오 3단계 이내 (화면에서 무엇을 누르고 무엇을 보는가)
3. 요구사항 → 기능 → 수용 기준 표
   `# | 요구사항(REQUIREMENTS.md 번호) | 기능 | 수용 기준(입력 → 기대 결과, 숫자로) | MVP 여부`
   수용 기준은 테스트로 바로 옮길 수 있게 쓴다. 예: "수량 0 입력 → 저장 거부, 오류 문구 표시"
4. 범위: MVP(필수) / 여유 있으면 / 하지 않음(이유). 필수 요구사항은 전부 MVP에 들어가야 한다.
5. 구현 순서: 세로 단위(화면+로직+데이터를 한 기능씩 끝까지)로 나눈 뒤, 각 단위를 다시 15분 이내 작업으로 쪼갠다(AGENTS.md 8-4). 표로 쓴다:
   `단위 | 작업 | 바뀌는 파일 | 확인 명령 | 예상 분 | 앞선 작업 | 병렬 묶음`
   예: 로직 함수 1개 + 단위 테스트 / API 1개 + 테스트 / 화면 1개. "웹앱 전체 만들기" 같은 작업은 금지.
   첫 작업은 가장 작게(데이터 읽기와 행 수 출력 등) 잡아 실제 속도를 잰다.
   서비스 먼저: 웹 서비스에 최적화가 붙는 과제는 첫 세로 단위를 가장 단순한 해법(modeling-options 4장 0~1단계)으로 입력 → 결과 → 화면까지 끝낸다. 화면은 MVP, 로그인은 담당자가 요구하면 MVP다. 결과 파일 형식(열 이름)을 먼저 고정하면 화면 단위와 방법 개선 단위를 다른 executor로 병렬 진행할 수 있다. 공용 파일(AGENTS.md 8-7)을 바꾸는 작업은 그 묶음 앞에 혼자 둔다. 방법 수준을 올리는 작업은 화면이 결과 파일을 읽어 표시한 뒤 합친다.
   병렬 묶음: 앞선 작업이 모두 끝나야 시작할 수 있고 바뀌는 파일이 서로 겹치지 않는 작업에는 같은 묶음 번호를 붙인다(AGENTS.md 8-7). 공용 파일(8-7 목록)을 만들거나 고치는 작업은 묶음 앞이나 뒤에 혼자 둔다. 시간 계산은 묶음 안에서 가장 긴 작업 기준.
   PROGRESS.md에는 `단위 | 작업 | 예상 분`을 옮기고 시작, 끝, 상태, 다음 행동 열을 더한다(AGENTS.md 8-5).
   webapp-build 6장 보안 기본값 중 채택할 항목은 이 표와 수용 기준 표에 MVP 행으로 넣는다(예: 이용자 토큰으로 운영자 API 호출 → 403). 계획 밖에서 조용히 구현하지 않는다.
5-1. 대기 중 할 일(실행자가 도는 동안 내가 할 것): 계획을 막지 않는 추가 질문, 다음 단위의 수용 기준 다듬기, 결정 카드 읽고 내 말로 설명해 보기, 방금 끝난 단위의 입력과 출력을 내 말로 말해 보기, Browser 점검표 초안.
6. 시간 체크포인트. PLAN.md 맨 위에 실제 과제 시작 시각 S를 적고 마감 E를 계산한다.
   E(제출물 확정 마감) = min(S + 과제 시간, 종료 시각 − 서술형 시간 − 문제 준비 대기 10분). 세 값은 당일 안내문에서 옮긴다(예: 180분, 14:00, 30분 → 13:20).
   계획 승인 S+25 / MVP 동작과 감사 1회 시작 E−60(AGENTS.md 0번, 남은 단위와 병렬) / 감사 높음 지적 수정 E−40 / 검증 완료 E−35 / 문서 완료 E−15 / 내가 직접 읽기 E−15~E−10 / 제출 시작 E−10.
   과제 시간 T가 180분보다 길면 MVP 동작과 감사 시작만 E − 60 × T/180으로 앞당겨 구현 뒤 여유를 늘린다(5분 단위 반올림). 계획 승인 S+25와 감사 높음 수정 이후의 E−40, E−35, E−15, E−10은 분 단위 그대로 둔다. T가 180분보다 짧으면 비율로 줄이지 말고 감사부터 빼서 PLAN.md에 다시 정하고 나에게 승인받는다. 안내문에 단계별 시각이 있으면 그 시각이 우선이다.
   첫 작업 2~3개의 실제 소요가 예상의 1.5 배를 넘으면 남은 예상 시간에 실제 배수를 곱해 다시 계산하고(이후 AGENTS.md 8-6의 "예상"은 이 재보정 값), MVP 동작 시각을 넘기는 단위를 "여유 있으면"으로 내린다.
   체크포인트를 넘기면 남은 단위를 "여유 있으면"으로 내리고 그 결정을 기록한다.
7. 위험: 기술 위험(미설치 패키지, 포트, 데이터 형식)과 해석 위험(판단 위임 항목) 각 1줄씩.

## 2. COLLAB_LOG.md (작업 내내 누적)
결정이 생길 때마다 한 줄 추가한다. 형식:
`시각 | 무엇을 AI에 맡겼나 | 결과 | 내가 확인한 방법 | 채택/수정/거절 + 이유`
- 담당자 답변으로 계획이 바뀐 경우, 범위를 줄인 경우, AI 제안을 거절한 경우는 반드시 기록한다.
- 오류나 장애(설치 실패, 도커, 포트, 테스트 실패)를 고친 경우는 결과 칸에 `발견 / AI 진단 / 내 판단`을, 확인 칸에 다시 돌린 명령과 결과를 적는다. (서술형에서 "기록한 문제를 어떻게 진단했나"를 묻는다.)
- 이 기록과 git log가 서술형 질문의 근거가 된다.
